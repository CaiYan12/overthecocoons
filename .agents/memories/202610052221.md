# 2026-10-05 22:21 — 光标语义档位滞留修复（`c6e8d1a`）+ 一个「测不出来的真实缺陷」

## 用户反馈与结论

用户实测：鼠标滑过占位版画下缘时，有概率出现「指针已不在版画上、标签仍显示 `OPEN`」的错位，并**自己猜对了方向**（怀疑与判定范围有关）。实测确认：**不是判定范围问题，是档位状态与指针下的元素失同步**。

## 根因（实测，非推断）

档位只由 `mouseover` 驱动，而**浏览器会在布局/动效变化后静默更新 hover 节点却不派发 `mouseover`**。两个方向都复现到了：

- 正向（用户截图）：指针已移到正文，标签仍是 `OPEN`。
- 反向：入场揭示动效收尾后指针下已是版画，标签却不亮（`elementFromPoint` = `.k-media-art`，标签 `opacity` 0）。

**关键细节（最容易做错的一步）**：此时连 `mousemove` 的 `event.target` 也取自那个陈旧的 hover 节点。埋点（把 `document.elementFromPoint` 包一层记录调用）实测：站点重判时 `elementFromPoint` 返回 `DIV.k-text`，而 `event.target` 仍是版画——所以「在 mousemove 里用 `event.target` 重判」单独并不够，**必须用 `document.elementFromPoint(clientX, clientY)` 重新做命中测试**。这是我第一版修复失败的原因。

修复：`applyTier(target)` + 档位键去重（避免每次移动重启补间），`mousemove` 与 `mouseover` 都走它；`mousemove` 侧用 `elementFromPoint` 而非 `event.target`。

## 最重要的一条经验：有些真实缺陷**测不出来**

曾花大量篇幅为该场景补 e2e 回归，两版都失败在「无法同时做到确定与有牙」：

1. **真实鼠标移动版**：浏览器会在指针下元素变化时补发 `mouseover`，被测路径被掩盖 → 变异验证（关掉 mousemove 重判）**仍能通过，即无牙**。而且它在 WebKit/Chromium 矩阵里随机失败（负载相关）。
2. **合成 `mousemove` 版**：只驱动站点处理器、不触发浏览器 hover 记账，看似理想；但浏览器会先行自愈（在合成事件之前就把档位修好了）→ 同样无牙。

**结论与处置**：该缺陷能否复现取决于浏览器是否在布局变化后自行补发 `mouseover`，**随时序与引擎而变**，本质是竞态。两版都不落测试，避免留下「永远绿却挡不住回归」的假保障；机制与证据写进票 #14 评论（issuecomment-5996396532）。**修复本身仍经变异验证与三引擎重复运行确认有效**——「有修复、无测试」是这里的诚实结论，不是遗漏。

**可复用判断**：当一条回归测试的「有牙」依赖于浏览器内部时序（而非被测代码的确定性行为）时，宁可不要它，也不要一条会随机失败或永远通过的测试。判断顺序：先变异验证（关掉修复看它是否失败）→ 有牙才留下。

## 调试手法沉淀

- **包一层 DOM API 记录调用**：`document.elementFromPoint` 被包后能直接看到「站点的重判实际算出了什么」，比读 CSS/猜状态快得多。本轮正是靠它发现「4 次调用都返回未标记元素，但 `event.target` 不是它」。
- **埋点区分「事件是否派发」与「处理函数是否执行」**：分别装 capture 计数器和 API 包装，二者不一致时问题就在「用错了事件字段」而不是「事件没来」。
- **对 dev 服务器跑探针**（`astro dev` 不占 `astro preview` 的全局锁），可比对「源码行为」与「产物行为」；本轮两者一致，排除了构建差异。
