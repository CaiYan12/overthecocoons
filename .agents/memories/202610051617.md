## 实测发现（Chromium headless，DPR 3，预览服务 127.0.0.1:4321）

1. **`mix-blend-mode: difference` 完全不生效**。浅色纸面 dot 实测 `#ffffff` vs 背景 `#f7f4eb` → 对比度 **1.09:1**（若混合生效应为 `rgb(7,10,19)` / 18.14:1）。
   根因（A/B 隔离实测，非规范推断）：`.k-cursor` 自身 `position: fixed` 即形成堆叠上下文 → **隔离组**，子元素的 `mix-blend-mode` 只能与组内（透明）背景混合，看不到页面。
   - 对照 A：裸 `position:fixed + z-index:900` 元素**自身**带 difference → 正常混合 ✅（`#13161f` = difference(白, `#ece9e0`)）
   - 对照 C：同元素套进 `fixed + z-index:900 + opacity:1` 的父级 → `#ffffff` ❌（排除 z-index / transform / opacity 单独致因；父级 opacity 0.99 同样隔离）
   - **可用修法（已验证）**：把 difference 移到 `.k-cursor` 容器上 → dot 实测 `#080b14`，对比度 **17.87:1** ✅
   - 代价：整棵子树作为一个组反相 → label 的 `--accent` 红会随背景漂移（浅色纸面上红 `#8F262B` → 计算值 `#69CFC1` 青绿）。要保标签原色必须把 label 移出 `.k-cursor`（结构 + motion.ts 加一对 quickTo）
2. **`border-width: 1.5px` 在 Blink 被取整为 1px**：计算值 `1px`、渲染 3 设备px @DPR3 = **1.00 CSS px**，亮度序列与 `1px` 逐字节相同 → #12 的「ring 边 1→1.5px」是**无效改动**（`2.5px`→`2px` 同理）。
   **替代**：`box-shadow: 0 0 0 1.5px` → 5 设备px = **1.67 CSS px**（spread 支持亚像素，带 1px 抗锯齿边）；`border-width:2px` → 2.00 CSS px。
3. 候选色对比度（机器计算，非手算）：浅色 paper 上 白=1.09:1 / ink=15.21:1 / accent=7.77:1；surface 上 白=1.02:1 / accent=8.32:1；深色 paper 上 白=17.74:1 / accent=6.96:1。difference(白) 明暗分别 18.14:1 / 14.34:1。
   → **#12 的设计意图（difference 恒最大对比）本身是对的，只是实现没生效**；`var(--accent)` 单色在明暗两主题均 ≥6.3:1，是可行的不依赖混合方案。
4. 综上：#12 三项改动只有 dot 6→8px 真正生效，其验收标准「明暗底色下均高对比」当前**不成立**。

## 复用方法（值得沉淀）

- **像素级实测法**：Playwright 截图 → 在页面内用 `canvas.drawImage` + `getImageData` 读回 → 得到渲染后真实 sRGB，再算 WCAG 对比度。比目测可靠，契合既有「对比度必须实测勿目测」教训（见 202610051435）。
- **根因隔离法**：把可疑 CSS 属性拆成独立对照元素注入真实页面逐个实测，而不是读规范推断成因。
- **采样陷阱**：`page.screenshot({clip})` 的 clip 会被视口夹紧，光标可能不在截图中心 → 必须用 `offX = x - clipX - W/2` 修正，否则会把背景色误读成光标色（本轮回踩过，第一轮结论一度错误）。
- 本机 `astro preview` 曾有僵尸进程占锁（PID 存活但不监听端口）→ `pnpm exec astro preview stop` 可清；服务已在本轮以 127.0.0.1:4321 后台运行。
