## 关键教训

**v2 我只核实了「选择器」，文案与动效对象仍照记忆写。** 核实做了一半，等于没核实——GPT 按我写错的文案去断言，必然报假失败。

**写规格/提示词时，每一个字符串常量、每一个「应有行为」都必须落到文件行号。** 选择器、类名、文案、动效作用对象、数值基线，五类全部同等对待，不存在「这个我肯定记得」。

**基线表要带实测时间戳**，且**表内合计必须与总数自洽**。v1 的 862 vs 865 矛盾是外部 agent 主动指出来的——我自己没发现，因为我只核对了单项、没做加总校验。

## 沉淀的检查动作

交付任何含「期望值」的文档前，逐项问：
1. 这个字符串/类名/选择器，我打开过对应源码文件吗？
2. 这个「应有行为」，我读过实现它的那个函数吗？
3. 数值基线是否做了**加总自洽**校验？是否标了实测时间？
4. 我描述的是**这个元素**的行为，还是另一个相似元素的行为？（面板动效 vs 光标动效就栽在这里）

## 附：本轮另一处独立教训

GitHub `schedule` 事件使用「工作流文件最后一次被修改时所在 commit」的 SHA，**不是 main HEAD**。`update-data.yml` 因此从 10-16 起连续 5 次定时抓取都跑 10-15 的旧代码 `cd2d444`，只抓百度，六源代码从未在定时任务中执行。修复：checkout 显式 `ref: main`（`ee329d2`）。**该缺陷长期无人发现的原因**：update-data 历史运行全部是 `schedule`，一次 `workflow_dispatch` 都没有，所以「手动正常、定时回退」的矛盾从未被触发。
